### D159 — intent_id is an eternal (kind, asset) idempotency key: retries are structurally impossible and counted as phantom progress
Anchors: planner.py:274 (intent_id = graph_key('intent', kind, asset.id)), 292-295
(pg_insert on_conflict_do_nothing on (campaign_id, intent_id)), 296-301 (select returns the
OLD terminal action on conflict), 861-862 ('created' += 1 regardless), _insert_intent shared
by deterministic _generate and LLM apply path.
Live proof (campaign 9a8cdb26, v9, with D97 overlay active): planner.autonomous_round events
report intents: 4 for rounds 9..18 straight, yet pentest_live_actions stayed at 7 rows
(max intent node round = 6, 0 soft-deletes) — every 'retry' collided with the original
intent_id, on_conflict_do_nothing silently no-op'd, and the same terminal action was
re-counted as created. The narration ('five fan-out intents dispatched') was true from the
LLM's view and empty from the DB's view; campaign could only await_planner-echo until killed.
This is the layer UNDER D97: the fence overlay re-opened proposals, but the idempotency key
has no attempt dimension, so an accepted proposal still cannot create a second action. The
DAG can never show a retry node; action history is capped at exactly one action per pair.
Fix shipped as overlay tonight (patch_d159_retry_ids.py): intent_id = graph_key('intent',
kind, asset, 'a{attempt}') where attempt = number of already-terminal actions for the pair
(computed by the D97 overlay block); _url_followup passes attempt through. Pair now gets 3
real attempts (0,1,2), each a distinct action + intent node; fence at 3 stays. Dev-side fix:
make retry a first-class contract field (attempt/parent_attempt_id on the intent), count
'created' only when pg_insert.rowcount==1, and give the action's unique key the attempt too
(UniqueConstraint intent_id is global, not per-campaign — worth revisiting).
Also note: D159 made the D110 double-count arithmetic (existing intents + actions) irrelevant
here because intents==actions 1:1 in this code, but that defect stands for the deterministic
path separately.

### D163 — ffuf builder has no soft-404 baseline: content-discovery facts are noise on soft-404 sites
Operator confirmed (2026-11-23): vodafone.com.tr serves a custom 404 page with HTTP 200 for
non-existent paths (live evidence: ffuf FUZZ='JtWHrEqx' random string -> status_code 200,
181081 bytes — the same page 'login' returned). toolchain._ffuf builds argv with no -recf/-fs/-fw
filter and the platform never issues a baseline request, so every non-existent path becomes a
content.discovered observation. Consequences: (a) planner builds goals/probes on phantom endpoints
(visible in v11: probes at /login /robots.txt /.env claims derived partly from noise); (b) any
status+word matcher (including the baked nuclei templates) matches the soft-404 body -> guaranteed
false findings; (c) the night's 'no finding' outcome is partly explained: real signal is buried in
200-soft-404 noise and WAF 403s.
Dev fix: ffuf builder should first crawl a random-path baseline (ffuf -recf with a generated
nonce path response is the canonical fix: add '-recf /work/soft404.html' produced by a prior
http_request_probe with a nonce path, or '-fs <len>' when length is stable), AND domain_store
should tag content.discovered rows whose (status,length,lines) equal the campaign's soft-404
profile. Until then: operators must treat 200s on this target as unverified.

### D164 — builder hardcodes per-action output caps that silently truncate crawl/probe evidence
Each toolchain builder hardcodes max_output_bytes (http_request_probe 64KB, katana 16MB,
httpx 4MB...) which _common forwards into the manifest and the platform takes as
min(cfg.output_max_bytes, spec.max_output_bytes). Consequences proven on vodafone.com.tr:
(a) the 622KB SPA-shell root page is delivered to the planner as only its first 64KB, so
API-base/route proof_markers in the remaining 558KB are unreachable and probes keep
'returned no proof_matches' -> planner re-probes; (b) every truncation point is silent to
the LLM: the observation quotes look complete. Fix: single output-budget policy knob in
_common (config-driven), builders stop hardcoding; report truncated:true into observations.

### D165 — platform sandbox_output_max_bytes (default 1MiB) silently corrupts large tool outputs

keep bodies out of the ingest file (separate capture path for evidence).
